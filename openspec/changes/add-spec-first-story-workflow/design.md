# Design

## Context

- `implement-story` runs ten steps on one `feature/` branch. Steps 3–5 (research, plan, approve plan) write the OpenSpec
  change. Steps 6–10 implement it, review it, open the PR, archive the change and merge.
- `finish-work` is shared by every workflow. Its Finalize history sub-step 4 decides whether to archive with
  `git diff --diff-filter=A origin/<default-branch>...HEAD -- openspec/changes`. That is, it archives only a change the
  branch adds.
- In the spec-first workflow, the spec branch adds the change but must not archive it. The implementation branch must
  archive the change but does not add it. The diff filter gets both cases wrong, while it stays right for
  `implement-story`.
- See `proposal.md` for the motivation.

## Goals / Non-Goals

**Goals:**

- Each of the two skills reads like `fix-bug` and `do-chore`: numbered steps, a model named per step, and approval gates
  kept in the skill.
- `finish-work` stays the only place that knows how to create, finalize and merge a PR.

**Non-Goals:**

- No change to `implement-story`, `write-story`, the issue forms, the PR template, the reviewer agent or
  `check-commits.sh`.
- No shared extraction of the research, plan and approve plan steps that `write-spec` repeats from `implement-story`.

## Decisions

### 1. The change is named before the branch

`write-spec` derives a kebab-case change name from the Story title before step 1, because the branch
`docs/<change-name>-spec` needs it. It passes that name to `openspec-propose`.

- Alternative considered: branch first as `docs/<story-slug>` and rename after planning. Rejected because renaming a
  branch mid-workflow is error-prone.
- Alternative considered: name the branch after the Story number. Rejected because the Story says `<change-name>`.

### 2. The proposal records the Story

The proposal gets a line `Story: #<n>` under its title. `implement-spec` reads it from `origin/<default-branch>` for
three uses: the `Refs: #<n>` trailer, the commit check and `Closes #<n>` in the PR. So the user names only the change.

- If the line is missing, for example in a change written by hand, `implement-spec` asks for the number.
- Alternative considered: ask the user for both the change and the Story every time. Rejected because it duplicates
  information the spec already holds and invites mismatches.
- Alternative considered: a field in `.openspec.yaml`. Rejected because that file is generated by the CLI, and its
  schema is not ours to extend.

### 3. Archiving is decided by the workflow, not by the diff

Finalize history sub-step 4 becomes:

- For `implement-spec`, archive the change it implements if `openspec/changes/<change-name>/` still exists on the
  branch. If it was already archived by an earlier run, skip.
- For `implement-story`, keep today's rule: archive the change the branch adds (`--diff-filter=A`).
- For every other workflow, skip.

Alternative considered: one diff-based rule for all workflows. Rejected because no diff tells a `write-spec` branch
(adds the change, must not archive) from an `implement-story` branch (adds the change, must archive).

The branch-name alternative (`feature/<change-name>`) was rejected because the workflow in use is already explicit in
every `finish-work` call, while a branch name can be typed wrong.

### 4. `docs/` branches belong to the Story

- `AGENTS.md` lists `docs/<change-name>-spec` with the other branch prefixes.
- Its `Refs:` trailer rule, and the commit check in `finish-work`, name `docs/` next to `feature/` and `fix/`.
- `check-commits.sh` does not read the branch name, so it is unchanged.

### 5. A spec PR uses the existing template

A spec PR fills the existing template, so the template stays generic:

- Type of change: Story.
- Related issues: `Refs #<n>`, which keeps the Story open.
- Checklist: the OpenSpec item is ticked.
- `finish-work` gets one rule for this case.

Alternative considered: a fourth type, Spec. Rejected because it touches the template, its spec and every adopter for
one checkbox.

### 6. Checking that the spec is merged

`implement-spec` step 0 fetches `<default-branch>` and checks
`git cat-file -e origin/<default-branch>:openspec/changes/<change-name>/proposal.md`. A path under `archive/` never
matches this path, so an archived change fails the check like a missing one.

### 7. Spec corrections in `implement-spec`

The correction rule of step 6 of `implement-story` is adapted to the merged spec:

- **Artifacts wrong:** revise them on the `feature/` branch with `openspec-update-change` on Opus 5.5, commit, get
  approval, resume. The revision is reviewed in the implementation PR.
- **Story intent wrong:**
  1. Stop.
  2. Ask the user to correct the Story and decide on the merged change and the committed work.
  3. Point to `write-spec` for the new spec.

### 8. Step layout

`write-spec`:

- 0 Check workflow setup
- 1 Create docs branch
- 2 Verify clean state
- 3 Research (Opus)
- 4 Plan (Opus)
- 5 Approve plan
- 6 Create PR
- 7 Finalize
- 8 Merge

`implement-spec`:

- 0 Check workflow setup
- 1 Create feature branch
- 2 Verify clean state
- 3 Implement
- 4 Review
- 5 Create PR
- 6 Archive
- 7 Merge

### 9. Routing a Story

The Implementation Workflow of `AGENTS.md` maps a Story to `write-spec` and then `implement-spec`. It maps a Story to
`implement-story` only when the user asks for it. A merged change goes to `implement-spec`.

Alternative considered: `implement-story` as the default. Rejected by the user.

The skill descriptions overlap, and `implement-story` cannot change. The routing line in `AGENTS.md` makes `write-spec` the default. `write-spec` also claims "work on, start, pick up a Story" in its description to support it.

### 10. The spec is reviewed before its PR

`write-spec` has the `reviewer` subagent review the docs branch before the PR, as `implement-story` does in step 7. `finish-work` maps the Implement step of `write-spec` to a fixup commit on the change's files and its Review step to this pass.

## Risks / Trade-offs

- [Two PRs per Story instead of one] → This is the point of the Story. The spec PR is small and fast to merge. Users
  who want one PR ask for `implement-story`.
- [`write-spec` repeats steps 3–5 of `implement-story`] → Accepted. These are two copies of short prose. A shared
  extraction would couple the two skills for little gain.
- [Unarchived changes pile up on the default branch between the two PRs] → `openspec list` shows them as work in
  flight, which is correct. `implement-spec` archives each one.
- [The descriptions of `write-spec` and `implement-story` both match "work on Story #n"] → Accepted. `AGENTS.md` does the routing and the descriptions only support it.
- [A spec merged but never implemented stays unarchived] → Accepted. The open Story makes it visible.

## Migration Plan

- This change runs under `implement-story`, with spec and code in one PR. Its Finalize history archives this change
  under the kept `implement-story` rule, so no special handling is needed.
- Rollback: revert the merge commit.
